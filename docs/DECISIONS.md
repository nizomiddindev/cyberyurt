# Architectural & Product Decisions

Every time a task introduces or changes a decision, add a new row to this table.

| Date | Decision | Why | Alternatives rejected |
| --- | --- | --- | --- |
| 2026-11-26 | Name the platform "CyberYurt" and store `siteName`, `terminalHost` (`yurt`), and `domain` (`cyberyurt.com`) in one file (`src/config/site.ts`) | "Yurt" means both home and homeland in Uzbek; keeping naming in one config file makes rebranding or localizing trivial | Hard-coding the platform name across pages and terminal prompts |
| 2026-11-26 | Stack: Next.js (App Router, TypeScript, `src/`), Tailwind CSS, Supabase (Postgres + Auth, RLS on every table), `xterm.js`, npm (deploy to Vercel later) | Fast full-stack TypeScript workflow, strong database-level access control via RLS, and low-cost/free hosting | Separate backend server (Express/Django) + self-hosted Postgres; Firebase without SQL |
| 2026-11-26 | All UI text in Uzbek Latin in `src/locales/uz.json` using `‘` (U+2018) in `o‘` and `g‘`, with no hard-coded UI strings | Proper Uzbek typography for teenagers in Uzbekistan while keeping Russian and English easy to add later | Hard-coding Uzbek strings in JSX; using ASCII apostrophe `'` |
| 2026-11-26 | Temporary plain neutral-gray Tailwind design isolated inside `src/components/ui/`; minimal text rule everywhere except lesson/docs content | Lets us swap in the final design system later in one folder without rewriting pages, and avoids cluttered marketing copy | Designing custom visuals up front; styling pages directly with scattered Tailwind classes |
| 2026-11-26 | Functionality first (build Milestones 1–6 in order before applying final visual design) | Proves core learning, terminal, and CTF workflows early for the Gulistan pilot class instead of getting stuck on mockups | Polishing visuals before core features work; building backlog items from `IDEAS.md` early |
| 2026-11-26 | Username rules (`a-z`, `0-9`, `_`, `-`, starts with a letter, 3–20 chars, unique; blocked: `root`, `admin`, `mehmon`, `system`, `guest`) + separate `display_name`; minimum data for minors; guests are `"mehmon"` with nothing saved | Safe for Linux prompts/paths and URLs, protects minors' privacy (public profile never shows real name/email/school), and lets visitors try without signing up | Allowing spaces/special characters in usernames; collecting unnecessary personal data; forcing login before trying |
| 2026-11-26 | Store terminal files ONLY in the browser via OPFS (never cloud storage); store progress/XP/solves in Supabase | Zero cloud file storage cost, instant local file access, and authoritative learning progress in Supabase | Storing student terminal files in cloud buckets; saving XP/progress in browser storage |
| 2026-11-26 | Key OPFS terminal storage by Supabase user ID (`/users/<user-id>/`), displayed as `/home/<username>` | Two students sharing one school PC never see each other's files, and renaming a username preserves files | Keying OPFS folders by username or a single shared folder |
| 2026-11-26 | Use `xterm.js` + TypeScript simulated shell now, and optional `v86` for real Linux in the browser later; never WebVM / CheerpX | Fast startup, zero per-student server cost, safe in-browser execution, and clean open-source licensing | WebVM / CheerpX (rejected due to license); cloud-hosted Linux containers per student |
| 2026-11-26 | Restrict terminal `wget` to our own domain (`cyberyurt.com`) | Lets students download static challenge files safely while preventing arbitrary external network fetches | Unrestricted `wget` to any URL; hosting challenge files on third-party servers |
| 2026-11-26 | Store only SHA-256 hashes of flags (`KIBER{...}`), verify flags server-side only via API route with max 5 attempts/minute/user, never send flags to the browser | Prevents students from finding flags in client code or brute-forcing submissions | Checking flags in client-side JavaScript; storing plaintext flags in the database |
| 2026-11-26 | Every CTF challenge includes `solve.py`, verified by `scripts/validate-challenges` | Guarantees every challenge is actually solvable and prints the exact expected flag before shipping | Manual-only challenge testing without automated verification |
| 2026-11-26 | Glossary terms live in `content/glossary/<term>.md`, referenced as `[[term]]` in lessons, and checked by `scripts/validate-lessons` (fails build if missing) | Ensures beginner-first education where every technical term is explained and prevents broken glossary links | Untracked inline definitions; leaving jargon unexplained |
| 2026-11-26 | Render lesson visuals (`::diagram tree`, `::diagram flow`, `::steps`, `::compare`) from code inside Markdown instead of image files | Keeps visual style consistent across lessons, supports interactivity, and makes Uzbek text easy to edit and translate | Static PNG/SVG diagram images created in external tools |
| 2026-11-26 | Ignore `.env*` with `!.env.example` in `.gitignore` | Ensures plain `.env` or `.env.production` files with secrets can never be accidentally committed while keeping `.env.example` tracked | Ignoring only `.env.local` and `.env*.local` |
| 2026-11-26 | Use `vitest` for unit tests and `lucide-react` for SVG icons | Fast zero-boilerplate TypeScript test runner for milestone tests and clean non-emoji SVG icons | Jest with extra TS config; emoji icons or hand-drawn SVG strings |
| 2026-11-26 | Restrict `profiles` table RLS to own-row read/write only, and expose username availability + public profile via narrow `SECURITY DEFINER` SQL functions | Protects minors' `display_name` and `class_name` from ever being queried by other users directly from Supabase while allowing public profile lookup and signup checks | Broad `SELECT` RLS policy on `profiles` readable by all authenticated or anonymous users |
| 2026-11-26 | Lock `role`, `xp`, `level`, `created_at` on `profiles` with a trigger that blocks the `anon`/`authenticated` Postgres roles (inserts are forced to student/0/1/now); only SQL Editor, `service_role` and `SECURITY DEFINER` functions may change them | The own-row update policy let any student set their own XP from the browser console, which would break the leaderboard; checking `current_user` (not `auth.uid()`) still lets future server-side XP functions work | Trusting the client not to send XP; checking `auth.uid()` (would also block legitimate `SECURITY DEFINER` XP awards); column-level `GRANT`s (easy to undo by accident with a later `GRANT ALL`) |
| 2026-11-27 | Share one `VirtualFileSystem` interface across `OpfsFileSystem` (logged-in users under `/users/<userId>/home/` + ephemeral in-memory `/tmp`) and `MemoryFileSystem` (guests `mehmon` + unit tests); store file contents as raw `Uint8Array` bytes | Guarantees guests save nothing, isolates students on shared PCs by user ID, makes `/tmp` always empty on each visit, lets all 27 commands run identically in Vitest, and supports binary CTF files (`file`, `strings`, `xxd`, `hexdump`, `base64`) | Storing files as UTF-8 strings only; persisting guest files in OPFS; duplicating shell logic for browser vs tests |
| 2026-11-27 | Load `@xterm/xterm` + `@xterm/addon-fit` dynamically client-only (`ssr: false`) inside `TerminalFrame` (`src/components/ui/`) and block redirects in `wget` (`redirect: "manual"` + domain allowlist) | Prevents SSR crashes since `xterm.js` requires `window`, keeps all visual styling inside `src/components/ui/`, and prevents `wget` from escaping our domain through HTTP redirects | Importing `xterm.js` directly in Server Components; allowing `fetch` to follow arbitrary cross-origin redirects |
| 2026-11-27 | Author lessons in Markdown (`content/lessons/*.md`) with YAML frontmatter, `[[slug\|label]]` glossary syntax, and YAML-bodied `::diagram tree`, `::diagram flow`, `::steps`, `::compare` blocks; enforce glossary/scenario/explanation checks in `prebuild` (`scripts/validate-lessons.mjs`) | Lets the owner author Uzbek lessons (including agglutinative suffixes) without writing code, ensures consistent editable diagrams, and fails the build automatically on missing glossary terms | Hardcoding lessons in TypeScript; storing diagrams as static images |
| 2026-11-27 | Keep all CTF plaintext flags out of git (read from gitignored `content/challenges/.flags.local.json` during `generate.py`); store only `flag_sha256` in `challenge.yaml` and `ctf_challenges`, verify flags + 5/min rate limit + hint deductions inside `SECURITY DEFINER` SQL functions (`submit_ctf_flag`, `unlock_ctf_hint`) called from server API routes, and validate every `solve.py` in `prebuild` | The GitHub repo is public and students must never read plaintext flags from git/client or forge solves/points directly in Supabase; `SECURITY DEFINER` also cleanly satisfies the `profiles` XP trigger | Storing plaintext flags in `challenge.yaml`/`generate.py`/tests; letting browser clients insert rows into `challenge_solves` or `profiles.xp` directly |
